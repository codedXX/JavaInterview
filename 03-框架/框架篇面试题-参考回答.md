## 框架篇面试题-参考回答

>##### **面试官**：Spring框架中的单例bean是线程安全的吗？
>
>**候选人**：
>
>嗯！
>
>不是线程安全的，是这样的
>
>当多用户同时请求一个服务时，容器会给每一个请求分配一个线程，这是多个线程会并发执行该请求对应的业务逻辑（成员方法），如果该处理逻辑中有对该单列状态的修改（体现为该单例的成员属性），则必须考虑线程同步问题。
>
>Spring框架并没有对单例bean进行任何多线程的封装处理。关于单例bean的线程安全和并发问题需要开发者自行去搞定。
>
>**比如：**我们通常在项目中使用的Spring bean都是不可变的状态(比如Service类和DAO类)，所以在某种程度上说Spring的单例bean是线程安全的。
>
>如果你的bean有多种状态的话（比如 View Model对象），就需要自行保证线程安全。最浅显的解决办法就是将多态bean的作用由“**singleton**”变更为“**prototype**”。
>
>> **所以面试中可以这样回答：**
>>
>> > Spring 单例 Bean 本身不保证线程安全。线程安全与否取决于 Bean 是否存在共享可变状态。无状态的单例 Bean 通常是线程安全的；如果有共享成员变量，就需要使用同步机制或改成无状态设计。
>

>（没看）**面试官**：Spring中的循环引用
>
>**候选人**：
>
>嗯，好的，我来解释一下
>
>循环依赖：循环依赖其实就是循环引用,也就是两个或两个以上的bean互相持有对方,最终形成闭环。比如A依赖于B,B依赖于A
>
>循环依赖在spring中是允许存在，spring框架依据三级缓存已经解决了大部分的循环依赖
>
>①一级缓存：单例池，缓存已经经历了完整的生命周期，已经初始化完成的bean对象
>
>②二级缓存：缓存早期的bean对象（生命周期还没走完）
>
>③三级缓存：缓存的是ObjectFactory，表示对象工厂，用来创建某个对象的
>
>
>
>**面试官**：那具体解决流程清楚吗？
>
>**候选人**：
>
>第一，先实例A对象，同时会创建ObjectFactory对象存入三级缓存singletonFactories  
>
>第二，A在初始化的时候需要B对象，这个走B的创建的逻辑
>
>第三，B实例化完成，也会创建ObjectFactory对象存入三级缓存singletonFactories  
>
>第四，B需要注入A，通过三级缓存中获取ObjectFactory来生成一个A的对象同时存入二级缓存，这个是有两种情况，一个是可能是A的普通对象，另外一个是A的代理对象，都可以让ObjectFactory来生产对应的对象，这也是三级缓存的关键
>
>第五，B通过从通过二级缓存earlySingletonObjects  获得到A的对象后可以正常注入，B创建成功，存入一级缓存singletonObjects  
>
>第六，回到A对象初始化，因为B对象已经创建完成，则可以直接注入B，A创建成功存入一次缓存singletonObjects 
>
>第七，二级缓存中的临时对象A清除 
>
>
>

>**面试官**：SpringMVC的执行流程知道嘛
>
>**候选人**：
>
>嗯，这个知道的，它分了好多步骤
>
>1、用户发送出请求到前端控制器DispatcherServlet，这是一个调度中心
>
>2、DispatcherServlet收到请求调用HandlerMapping（处理器映射器）。
>
>3、HandlerMapping找到具体的处理器(可查找xml配置或注解配置)，生成处理器对象及处理器拦截器(如果有)，再一起返回给DispatcherServlet。
>
>4、DispatcherServlet调用HandlerAdapter（处理器适配器）。
>
>5、HandlerAdapter经过适配调用具体的处理器（Handler/Controller）。
>
>6、Controller执行完成返回ModelAndView对象。
>
>7、HandlerAdapter将Controller执行结果ModelAndView返回给DispatcherServlet。
>
>8、DispatcherServlet将ModelAndView传给ViewReslover（视图解析器）。
>
>9、ViewReslover解析后返回具体View（视图）。
>
>10、DispatcherServlet根据View进行渲染视图（即将模型数据填充至视图中）。
>
>11、DispatcherServlet响应用户。
>
>当然现在的开发，基本都是前后端分离的开发的，并没有视图这些，一般都是handler中使用Response直接结果返回
>

>（重点）**面试官**：Springboot自动配置原理
>
>**候选人**：
>
>嗯，好的，它是这样的。
>
>在Spring Boot项目中的引导类上有一个注解@SpringBootApplication，这个注解是对三个注解进行了封装，分别是：
>
>- @SpringBootConfiguration
>
>- @EnableAutoConfiguration
>
>- @ComponentScan
>
>其中`@EnableAutoConfiguration`是实现自动化配置的核心注解。 
>
>该注解通过`@Import`注解导入对应的配置选择器。关键的是内部就是读取了该项目和该项目引用的Jar包的的classpath路径下**META-INF/spring.factories**文件中的所配置的类的全类名。 
>
>在这些配置类中所定义的Bean会根据条件注解所**指定的条件来决定**是否需要将其导入到Spring容器中。
>
>一般条件判断会有像`@ConditionalOnClass`这样的注解，判断是否有对应的class文件，如果有则加载该类，把这个配置类的所有的Bean放入spring容器中使用。

> Spring中事务失效的场景？：
>
> * 情况一：这样不加try/catch也会回滚
>
>   ~~~python
>   @Transactional
>   public void update(Integer from, Integer to, Double money) {
>           //转账的用户不能为空
>           Account fromAccount = accountDao.selectById(from);
>           //判断用户的钱是否够转账
>           if (fromAccount.getMoney() - money >= 0) {
>               fromAccount.setMoney(fromAccount.getMoney() - money);
>               accountDao.updateById(fromAccount);
>   
>               //异常
>               int a = 1/0;
>   
>               //被转账的用户
>               Account toAccount = accountDao.selectById(to);
>               toAccount.setMoney(toAccount.getMoney() + money);
>               accountDao.updateById(toAccount);
>           }
>   }
>   ~~~
>
> * 情况二：这个不会回滚，因为FileNotFoundException是受检异常,Spring 默认**不会回滚**
>
>   ~~~python
>   @Transactional
>   public void update(Integer from, Integer to, Double money) throws FileNotFoundException {
>       //转账的用户不能为空
>       Account fromAccount = accountDao.selectById(from);
>       //判断用户的钱是否够转账
>       if (fromAccount.getMoney() - money >= 0) {
>           fromAccount.setMoney(fromAccount.getMoney() - money);
>           accountDao.updateById(fromAccount);
>     
>           //读取文件
>           new FileInputStream("dddd");
>     
>           //被转账的用户
>           Account toAccount = accountDao.selectById(to);
>           toAccount.setMoney(toAccount.getMoney() + money);
>           accountDao.updateById(toAccount);
>       }
>   }
>   ~~~
>
> 
>
> **受检异常和非受检异常:**
>
> | 类型       | 典型例子                                                     | 编译器是否强制处理 | Spring 默认是否回滚 |
> | ---------- | ------------------------------------------------------------ | ------------------ | ------------------- |
> | 受检异常   | `IOException`、`FileNotFoundException`、`SQLException`       | 是                 | 否                  |
> | 非受检异常 | `RuntimeException`、`NullPointerException`、`IllegalArgumentException` | 否                 | 是                  |
>
> 
>
> **为什么加了rollbackFor就会回滚？**
>
> 因为 `rollbackFor` 就是在给 Spring 的事务管理器配置“回滚判断规则”。
>
> 默认规则大致是：
>
> ```python
> @Transactional
> ```
>
> 等价于告诉 Spring：
>
> ```python
> 遇到 RuntimeException 或 Error -> 回滚
> 遇到普通 Exception 子类        -> 提交
> ```
>
> 而 `FileNotFoundException` 属于普通 `Exception` 子类，所以默认会提交。
>
> 加上：
>
> ```python
> @Transactional(rollbackFor = FileNotFoundException.class)
> ```
>
> `相当于额外告诉 Spring：`
>
> ```python
> 遇到 FileNotFoundException -> 也要回滚
> ```
>
> 
>
> **【遇到普通 Exception 子类  -> 提交】这句话是什么意思？意思是 Exception子类都不会回滚吗？**
>
> 默认情况下，基本可以这样理解：
>
> ```
> Exception 的子类，但不是 RuntimeException 的子类
> => Spring 默认不回滚
> ```
>
> 例如这些默认不回滚：
>
> ```
> IOException
> FileNotFoundException
> SQLException
> ```
>
> 但要注意：`RuntimeException` 本身也是 `Exception` 的子类，它默认会回滚：
>
> ```
> NullPointerException
> ArithmeticException
> IllegalArgumentException
> ```
>
> 所以更准确的继承关系是：
>
> ```
> Exception
> ├── RuntimeException       -> 默认回滚
> │   ├── NullPointerException
> │   ├── ArithmeticException
> │   └── IllegalArgumentException
> │
> └── 其他受检异常             -> 默认不回滚
>     ├── IOException
>     │   └── FileNotFoundException
>     └── SQLException
> ```
>
> 也就是说，“普通 `Exception` 子类不回滚”指的是**排除 `RuntimeException` 这一支之后的受检异常**。
>
> 当然，添加：
>
> ```
> @Transactional(rollbackFor = Exception.class)
> ```
>
> 后，以上两类异常都会触发回滚。

 

> ⭐⭐**共享可变状态、有状态 Bean、无状态 Bean的三个例子，并且标出这三个的定义**
>
> 
>
> 这三个概念有交集，但不是同一回事。
>
> ### 1. 共享可变状态
>
> 定义：
>
> > 同一份数据被多个线程或请求共同访问，并且数据可能被修改。
>
> ```
> @Service // 默认是单例 Bean
> public class CounterService {
>     private int count = 0;
> 
>     public void increment() {
>         count++;
>     }
> }
> ```
>
> 这里的 `count`：
>
> - 是可变的；
> - 所有线程共享同一个 `CounterService` 实例；
> - 因此属于共享可变状态；
> - 这个 Bean 同时也是有状态 Bean；
> - `count++` 还存在线程安全问题。
>
> ------
>
> ### 2. 有状态 Bean
>
> 定义：
>
> > Bean 会保存能够影响后续行为或结果的数据。
>
> ```
> @Component
> @Scope("prototype")
> public class ShoppingCart {
>     private final List<String> items = new ArrayList<>();
> 
>     public void add(String item) {
>         items.add(item);
>     }
> 
>     public List<String> getItems() {
>         return items;
>     }
> }
> ```
>
> `ShoppingCart` 会保存购物车商品，因此是有状态 Bean。
>
> 这里使用 `prototype` 作用域，每次获取通常得到一个新实例，不同实例之间的购物车数据不共享，所以它不一定构成“共享可变状态”。
>
> 注意：有状态 Bean 如果是默认单例，就很容易变成共享可变状态。
>
> ------
>
> ### 3. 无状态 Bean
>
> 定义：
>
> > Bean 不保存某次请求的可变业务数据，方法结果主要由当前参数和依赖决定。
>
> ```
> @Service
> public class UserService {
>     private final UserRepository userRepository;
> 
>     public User findUser(Long id) {
>         return userRepository.findById(id);
>     }
> }
> ```
>
> 这个 Bean：
>
> - 没有保存用户请求数据的可变成员变量；
> - `id` 是方法参数，每次调用独立；
> - `userRepository` 是依赖引用，不是请求状态；
> - 因此通常属于无状态 Bean。
>
> 可以这样记：
>
> ```
> 无状态 Bean：不保存可变业务状态
> 
> 有状态 Bean：保存了会影响后续行为的数据
> 
> 共享可变状态：有一份可变数据，被多个线程共同访问
> ```
>
> 三者关系通常是：
>
> ```
> 默认单例 Bean + 可变成员变量
>                 ↓
>           有状态 Bean
>                 ↓
>        共享可变状态
> ```



> ⭐**用大白话告诉我一、二级缓存解决的是什么问题？**
>
> 用大白话说：
>
> 假设数据库是一个“档案室”。
>
> 
>
> **一级缓存解决什么问题？**
>
> 同一个人短时间内反复查同一份资料。
>
> 比如同一个 `SqlSession` 里：
>
> ```
> 第一次：查用户 1 → 去数据库拿
> 第二次：再查用户 1 → 直接用刚才拿到的
> ```
>
> 它解决的是：
>
> > 同一个会话里，避免重复访问数据库。
>
> 一级缓存范围小，只对当前 `SqlSession` 有效。
>
> 
>
> **二级缓存解决什么问题？**
>
> 不同的人都来查同一份资料。
>
> ```
> 请求 A：查用户 1 → 去数据库拿，并放入二级缓存
> 请求 B：查用户 1 → 直接使用缓存，不再查数据库
> ```
>
> 它解决的是：
>
> > 多个会话之间共享查询结果，减少数据库压力。
>
> 
>
> **最简单的区别**
>
> - 一级缓存：**我自己刚查过，别再查了。**
> - 二级缓存：**别人刚查过，大家都可以直接用。**
>
> 但缓存里的数据可能不是最新的，所以数据经常变化的业务要谨慎使用二级缓存。



> ⭐**什么情况下是相同的SqlSession，什么情况下不是相同的SqlSession？**
>
> 对，日常使用 Spring Boot + MyBatis 时，你可以这样理解：
>
> **相同的 SqlSession：**
>
> > `同一个数据库事务`里的多次 Mapper 操作。
>
> 例如一个带有 `@Transactional` 的业务方法中，连续查询用户、订单、商品，这些操作通常使用同一个 SqlSession，因此可以共享一级缓存。
>
> **不同的 SqlSession：**
>
> - 不同的数据库事务；
> - 不同的请求；
> - 事务已经结束后重新发起的操作；
> - `没有事务时`，`连续两次 Mapper 调用也不要默认认为是同一个 SqlSession。`
>
> 最重要的一句话：
>
> > **在 Spring 中，通常是“同一个事务 = 同一个 SqlSession”；不同事务 = 不同 SqlSession。**
>
> 所以一级缓存主要是在**同一个事务范围内**发挥作用。

> ⭐**那在@Transactional里，要两次相同的查询才会命中一级缓存吗？**基本可以这样理解：
>
> > 在同一个 `@Transactional` 事务中，对同一条 Mapper 查询、使用相同参数，第二次查询通常会命中一级缓存。
>
> 例如：
>
> ```
> 第一次：查询用户 id=1 → 查数据库
> 第二次：查询用户 id=1 → 读一级缓存
> ```
>
> 但要满足几个条件：
>
> - 必须处于同一个事务；
> - 查询语句和参数相同；
> - 中间不能执行增、删、改操作；
> - 中间不能手动清空缓存。
>
> 如果中间执行了更新：
>
> ```
> 查询用户 id=1 → 查数据库
> 更新用户 id=1 → 清空一级缓存
> 查询用户 id=1 → 再查数据库
> ```
>
> 另外，即使 SQL 文本看起来一样，如果是不同的 Mapper 方法，也不一定能命中，因为 MyBatis 还会区分具体的 Mapper 查询语句。

> **⭐如果方法没加@Transactional的话，方法里的多次相同查询也不会命中以及缓存是吗？**
>
> 
>
> **通常不会命中，但不是绝对。**
>
> 在 Spring Boot + MyBatis 的日常配置下：
>
> - 当前方法没有 `@Transactional`；
> - 调用了两次相同的 Mapper 查询；
>
> 这两次调用通常会被当成两次独立操作，一级缓存不会保留到第二次，所以通常会再次查询数据库。
>
> 但如果这个方法是被另一个带有 `@Transactional` 的方法调用的，那么它会加入外层事务。此时，即使当前方法自己没写 `@Transactional`，两次查询仍可能共享一级缓存。
>
> 所以准确说法是：
>
> > **是否命中一级缓存，关键看当前调用链上有没有同一个事务，而不是只看当前方法有没有写 `@Transactional`。**
