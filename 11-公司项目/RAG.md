## 【中等】创建知识库的流程是什么？使用 rag 切分检索的主要思路是什么？

真正可用的知识库，一般要分成两段看：

- **第一段是入库流程怎么做**
- **第二段是检索链路怎么设计。**

先说创建知识库的流程。我一般会这么做：

- 第一步不是直接切分，而是先做**数据接入和清洗**。因为知识源通常很杂，可能有 PDF、Word、Excel、网页、FAQ、内部文档，甚至截图 OCR。这里先要解决的是格式统一、乱码、页眉页脚、重复段落、脏数据这些问题。否则后面切得再好，检索质量也会被脏数据拖垮。
- 第二步是做**文档解析和结构化**。比如标题、章节、表格、列表、问答对、时间、产品名、版本号这些信息，我一般都会尽量提出来，变成 metadata。因为真实检索里，光靠向量相似度不够，后面往往还要结合 metadata 过滤，比如只搜某个产品线、某个时间范围、某个知识库版本。
- 第三步才是**分块**。这里我一般不会一刀切按固定字数硬切。更常见的做法是**“语义边界优先，长度控制兜底”**。比如优先按标题、段落、问答对、表格块去切，如果某一段太长，再做二次切分。然后再加一点 overlap，保留前后 1 到 3 句，避免上下文断裂。

  这里的核心取舍是：

  **chunk 太大**，召回可能不准，噪音多；

  **chunk 太小**，信息不完整，模型拿到后也答不明白。

  所以我不会拍脑袋定 chunk 大小，一般会拿真实 query 去测召回效果。

- 第四步是**向量化和建索引**。把 chunk 用 embedding 模型转成向量，写入向量库，同时把 chunk 原文、metadata、文档版本这些一起存进去。很多人只关注 embedding 模型，但我觉得索引设计、字段设计、版本管理同样重要，不然后面做增量更新、灰度发布会很痛苦。
- 第五步是**评测和迭代**。知识库不是建完就结束了，要拿一批真实问题做离线评测，看召回率、命中率、TopK 命中位置、最终回答准确率。如果效果差，再回头看是解析有问题、切分有问题，还是检索策略有问题。

再说 RAG 切分检索的主要思路。

它本质上是在做一件事：**先尽量找到对的上下文，再让模型基于这些上下文去回答。**

所以切分的目标，不是机械拆文本，而是让每个 chunk 都尽量成为一个 **“可被独立召回、又能表达完整意思”** 的信息单元。

比如 FAQ 场景我更倾向按问答对切；产品文档更适合按标题和小节切；表格类内容可能要单独转成结构化文本，不然检索很容易失真。

检索这块，一般也不是只做单路向量召回。更稳一点的做法通常是：

- 先做 query 理解，看要不要改写、补全、做意图识别；
- 然后做**多路召回**，比如向量召回 + 关键词召回 + metadata 过滤；
- 把候选结果捞出来之后，再做 **rerank 重排**；
- 最后把前几条最相关的 chunk 拼进 prompt，让模型生成答案。

有些场景还会要求引用来源、返回片段位置，方便用户校验。

这里面最关键的工程判断是：**RAG 的效果，不是某一个模型单点决定的，而是“切分质量 + 召回策略 + 重排能力 + Prompt 约束”共同决定的。**

我自己会特别注意几个坑：

- 一个是 **chunk 切得看起来很工整，但不符合用户提问方式**。比如用户问的是一个完整流程，但你切出来都是碎片句子，这种就很难答好。
- 一个是 **只做向量召回，不做关键词兜底**。像产品名、错误码、版本号这种精确词，纯语义检索不一定稳。
- 还有一个是 **知识库更新后没有版本管理**，结果新旧内容混着召回，线上会很乱。

所以如果让我总结，我会说：

**知识库建设的重点，不是“存进去”，而是“能不能被稳定、准确、可控地找出来”；RAG 的重点，也不是“检索到了”，而是“检索到的内容能不能刚好支持模型回答这个问题”。**

最后总结来说：

知识库不是把文档塞进向量库，而是先清洗解析、再按语义合理切分、再做多路召回和重排，最终让模型拿到“刚好够用的正确上下文”去回答。







> ⭐
>
> 这次按**实际执行顺序**说明，把正文清洗放在文档解析之后：
>
> **数据接入 → 文档解析和结构化 → 内容清洗 → 分块 → 向量化和建索引 → 评测迭代。**
>
> 然后再看用户提问时的检索流程。下面始终使用同一份虚构文档作为示例。
>
> 假设 `考勤系统使用手册.pdf` 中有：
>
> ```
> 第1页：
> 考勤系统使用手册
> 产品：考勤系统
> 版本：2.1
> 
> 第3页：
> 公司内部资料                  ← 重复页眉
> 
> 第三章 休假管理
> 3.1 年假规则
> 连续工作满一年的员工，每年享有
> 五天年假。
> 
> 3.2 申请流程
> 打开“休假申请”，选择“年假”，填写日期并提交。
> 
> 第3页                         ← 页脚
> ```
>
> **1. 数据接入：把文件拿到系统里，登记来源**
>
> 这一阶段处理的是文件本身：
>
> - 从上传、网盘、网站等渠道获取文件。
> - 检查文件能否读取、属于什么类型。
> - 记录来源、接入时间等信息。
> - 用文件哈希判断是否重复，避免重复入库。
>
> **此时不需要提取正文、识别章节。**
>
> 示例输出：
>
> ```
> {
>   "document_id": "doc-001",
>   "file_name": "考勤系统使用手册.pdf",
>   "file_type": "application/pdf",
>   "storage_key": "documents/doc-001.pdf",
>   "source": "内部知识库上传",
>   "status": "ready_to_parse"
> }
> ```
>
> 其中 `storage_key` 用来找到原文件。下一步解析的是这个文件。
>
> **2. 文档解析和结构化：读懂文件的内容及组织方式**
>
> 这一阶段根据文件类型调用解析器：
>
> - PDF：提取文字、页面位置、字号等；扫描页执行 OCR。
> - Word：读取标题、段落、列表、表格。
> - 网页：解析页面中的正文和其他元素。
>
> 再识别文档标题、章节层级、正文、表格等，从内容中提取产品名、版本号等属性。
>
> 示例输出，省略部分字段：
>
> ```
> {
>   "document_id": "doc-001",
>   "metadata": {
>     "title": "考勤系统使用手册",
>     "product": "考勤系统",
>     "version": "2.1"
>   },
>   "pages": [
>     {
>       "page": 3,
>       "elements": [
>         {
>           "type": "header",
>           "text": "公司内部资料"
>         },
>         {
>           "type": "heading",
>           "level": 1,
>           "text": "第三章 休假管理"
>         },
>         {
>           "type": "heading",
>           "level": 2,
>           "text": "3.1 年假规则"
>         },
>         {
>           "type": "paragraph",
>           "text": "连续工作满一年的员工，每年享有\n五天年假。"
>         },
>         {
>           "type": "heading",
>           "level": 2,
>           "text": "3.2 申请流程"
>         },
>         {
>           "type": "paragraph",
>           "text": "打开“休假申请”，选择“年假”，填写日期并提交。"
>         },
>         {
>           "type": "footer",
>           "text": "第3页"
>         }
>       ]
>     }
>   ]
> }
> ```
>
> **此时文件已经变成可处理的结构化内容，但里面仍可能有重复页眉、错误断行等干扰。** 实际解析器的输出能力不同，标题和页眉等角色有时需要结合布局或规则进一步识别。
>
> **3. 内容清洗：清除干扰，保留正文和有用结构**
>
> 在解析结果上进行清洗：
>
> - 删除重复页眉页脚。
> - 修复由排版造成的错误断行。
> - 处理异常空白、乱码、重复段落。
> - 保留标题、表格关系、适用条件和来源位置。
>
> 清洗后的结果可以组织成：
>
> ```
> {
>   "document_id": "doc-001",
>   "metadata": {
>     "title": "考勤系统使用手册",
>     "product": "考勤系统",
>     "version": "2.1"
>   },
>   "sections": [
>     {
>       "heading_path": ["第三章 休假管理", "3.1 年假规则"],
>       "page": 3,
>       "text": "连续工作满一年的员工，每年享有五天年假。"
>     },
>     {
>       "heading_path": ["第三章 休假管理", "3.2 申请流程"],
>       "page": 3,
>       "text": "打开“休假申请”，选择“年假”，填写日期并提交。"
>     }
>   ]
> }
> ```
>
> 正文里的“第3页”被删除了，但结构中的 `page: 3` 被保留。**删除页面上的干扰文字，不会删除系统记录的页面归属。**
>
> **4. 分块：形成可以独立检索、意思完整的内容单元**
>
> 利用章节、段落、表格、问答对等边界进行切分。只有内容过长时，才进一步按长度拆分，并按需要添加 overlap。
>
> 这个例子可以形成两个 chunk：
>
> ```
> [
>   {
>     "chunk_id": "chunk-001",
>     "text": "休假管理 > 年假规则\n连续工作满一年的员工，每年享有五天年假。",
>     "metadata": {
>       "document_id": "doc-001",
>       "source_file": "考勤系统使用手册.pdf",
>       "page": 3,
>       "product": "考勤系统",
>       "version": "2.1",
>       "section": "年假规则"
>     }
>   },
>   {
>     "chunk_id": "chunk-002",
>     "text": "休假管理 > 申请流程\n打开“休假申请”，选择“年假”，填写日期并提交。",
>     "metadata": {
>       "document_id": "doc-001",
>       "source_file": "考勤系统使用手册.pdf",
>       "page": 3,
>       "product": "考勤系统",
>       "version": "2.1",
>       "section": "申请流程"
>     }
>   }
> ]
> ```
>
> 这里把“连续工作满一年”和“五天年假”放在同一个块里，避免召回结果丢掉适用条件。
>
> **第二步识别的是文档结构；第四步决定这些结构中的内容如何组成检索单元。** 一个小节可能形成一个块，也可能因为太长而形成多个块。
>
> **5. 向量化和建索引：把 chunk 变成可搜索的数据**
>
> 给每个 chunk 计算 embedding，并存储：
>
> ```
> chunk_id：chunk-001
> text：休假管理 > 年假规则……
> vector：[0.12, -0.08, 0.31, ...]
> metadata：产品、版本、文件名、页码、小节等
> ```
>
> 向量数字仅作示意。
>
> 同时，根据检索方案建立关键词索引和 metadata 过滤能力：
>
> | 数据             | 用途                       |
> | ---------------- | -------------------------- |
> | 向量             | 找语义相近的内容           |
> | 正文的关键词索引 | 匹配产品名、术语、错误码等 |
> | metadata         | 限定产品、版本、时间范围   |
> | 正文与来源位置   | 给模型提供证据，生成引用   |
>
> **6. 评测和迭代：验证能否找到正确依据、给出正确答案**
>
> 准备测试问题及预期依据，运行完整检索和回答流程。
>
> 例如：
>
> | 测试问题               | 预期依据             | 检查重点                   |
> | ---------------------- | -------------------- | -------------------------- |
> | 工作满一年有几天年假？ | `chunk-001`          | 回答“五天”                 |
> | 年假怎么申请？         | `chunk-002`          | 申请步骤完整               |
> | 刚入职也有五天年假吗？ | `chunk-001`          | 保留“连续工作满一年”的条件 |
> | 2.1 版怎么申请年假？   | 2.1 版的 `chunk-002` | 不混入其他版本             |
>
> 如果结果有问题，就回头定位：
>
> - 正文提取错了：修解析或 OCR。
> - 适用条件被切丢了：调整分块。
> - 正确块没有召回：调整检索策略。
> - 找到了正确块，回答仍错：调整生成约束。
>
> 这一步产出的是评测报告和改进项。它会反复执行，覆盖下面的在线检索链路。
>
> 用户提问后，系统继续执行以下步骤。假设问题是：
>
> > 考勤系统 2.1 版，工作满一年有几天年假，怎么申请？
>
> **7. Query 理解：确定问题意图和检索范围**
>
> 识别两个需要回答的问题，以及明确的过滤条件：
>
> ```
> {
>   "queries": [
>     "工作满一年，每年有几天年假？",
>     "年假申请流程"
>   ],
>   "filters": {
>     "product": "考勤系统",
>     "version": "2.1"
>   }
> }
> ```
>
> 这里的版本条件来自用户的问题，不需要模型猜测。
>
> **8. 多路召回：找出可能回答问题的内容**
>
> 在指定产品、版本的范围内：
>
> - 向量检索找到语义相关的块。
> - 关键词检索匹配“年假”“申请”等词。
> - 合并两路结果，去掉重复块。
>
> 示例候选结果：
>
> ```
> chunk-001：年假规则
> chunk-002：申请流程
> ```
>
> metadata 负责限定检索范围；向量和关键词负责寻找相关内容。
>
> **9. Rerank 重排：从候选中挑选最有用的依据**
>
> 重排模型结合完整问题，进一步判断候选块能否回答它。
>
> 这个问题包含“几天”和“怎么申请”，所以需要保留两个块。如果候选中还有“病假申请”“考勤打卡”等内容，就应降低它们的排序。
>
> **10. 组装上下文并生成答案：让模型根据依据作答**
>
> 把问题、选中的 chunk、来源信息和回答要求一起交给模型：
>
> ```
> 回答要求：
> 依据提供的资料回答，保留适用条件，并标注来源。
> 
> 资料1：
> 连续工作满一年的员工，每年享有五天年假。
> 来源：考勤系统使用手册.pdf，第3页，版本2.1。
> 
> 资料2：
> 打开“休假申请”，选择“年假”，填写日期并提交。
> 来源：考勤系统使用手册.pdf，第3页，版本2.1。
> ```
>
> 最终答案示例：
>
> > 根据考勤系统 2.1 版手册，连续工作满一年的员工每年享有五天年假。申请时，打开“休假申请”，选择“年假”，填写日期并提交。
> > 来源：考勤系统使用手册.pdf，第 3 页。
>
> **这个流程中，来源和页码在读取时获取，章节和属性在解析时识别，清洗保留这些信息，分块继承它们，检索后再用于过滤和引用。**
