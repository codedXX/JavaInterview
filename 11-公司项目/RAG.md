## 【中等】创建知识库的流程是什么？使用 rag 切分检索的主要思路是什么？

真正可用的知识库，一般要分成两段看：

- **第一段是入库流程怎么做**
- **第二段是检索链路怎么设计。**

先说创建知识库的流程。我一般会这么做：

- 第一步不是直接切分，而是先做**数据接入和清洗**。因为知识源通常很杂，可能有 PDF、Word、Excel、网页、FAQ、内部文档，甚至截图 OCR。这里先要解决的是格式统一、乱码、页眉页脚、重复段落、脏数据这些问题。否则后面切得再好，检索质量也会被脏数据拖垮。
- 第二步是做**文档解析和结构化**。比如标题、章节、表格、列表、问答对、时间、产品名、版本号这些信息，我一般都会尽量提出来，变成 metadata。因为真实检索里，光靠向量相似度不够，后面往往还要结合 metadata 过滤，比如只搜某个产品线、某个时间范围、某个知识库版本。
- 第三步才是**分块**。这里我一般不会一刀切按固定字数硬切。更常见的做法是**“语义边界优先，长度控制兜底”**。比如优先按标题、段落、问答对、表格块去切，如果某一段太长，再做二次切分。然后再加一点 overlap，保留前后 1 到 3 句，避免上下文断裂。

  这里的核心取舍是：

  **chunk 太大**，召回可能不准，噪音多；

  **chunk 太小**，信息不完整，模型拿到后也答不明白。

  所以我不会拍脑袋定 chunk 大小，一般会拿真实 query 去测召回效果。

- 第四步是**向量化和建索引**。把 chunk 用 embedding 模型转成向量，写入向量库，同时把 chunk 原文、metadata、文档版本这些一起存进去。很多人只关注 embedding 模型，但我觉得索引设计、字段设计、版本管理同样重要，不然后面做增量更新、灰度发布会很痛苦。
- 第五步是**评测和迭代**。知识库不是建完就结束了，要拿一批真实问题做离线评测，看召回率、命中率、TopK 命中位置、最终回答准确率。如果效果差，再回头看是解析有问题、切分有问题，还是检索策略有问题。

再说 RAG 切分检索的主要思路。

它本质上是在做一件事：**先尽量找到对的上下文，再让模型基于这些上下文去回答。**

所以切分的目标，不是机械拆文本，而是让每个 chunk 都尽量成为一个 **“可被独立召回、又能表达完整意思”** 的信息单元。

比如 FAQ 场景我更倾向按问答对切；产品文档更适合按标题和小节切；表格类内容可能要单独转成结构化文本，不然检索很容易失真。

检索这块，一般也不是只做单路向量召回。更稳一点的做法通常是：

- 先做 query 理解，看要不要改写、补全、做意图识别；
- 然后做**多路召回**，比如向量召回 + 关键词召回 + metadata 过滤；
- 把候选结果捞出来之后，再做 **rerank 重排**；
- 最后把前几条最相关的 chunk 拼进 prompt，让模型生成答案。

有些场景还会要求引用来源、返回片段位置，方便用户校验。

这里面最关键的工程判断是：**RAG 的效果，不是某一个模型单点决定的，而是“切分质量 + 召回策略 + 重排能力 + Prompt 约束”共同决定的。**

我自己会特别注意几个坑：

- 一个是 **chunk 切得看起来很工整，但不符合用户提问方式**。比如用户问的是一个完整流程，但你切出来都是碎片句子，这种就很难答好。
- 一个是 **只做向量召回，不做关键词兜底**。像产品名、错误码、版本号这种精确词，纯语义检索不一定稳。
- 还有一个是 **知识库更新后没有版本管理**，结果新旧内容混着召回，线上会很乱。

所以如果让我总结，我会说：

**知识库建设的重点，不是“存进去”，而是“能不能被稳定、准确、可控地找出来”；RAG 的重点，也不是“检索到了”，而是“检索到的内容能不能刚好支持模型回答这个问题”。**

最后总结来说：

知识库不是把文档塞进向量库，而是先清洗解析、再按语义合理切分、再做多路召回和重排，最终让模型拿到“刚好够用的正确上下文”去回答。
